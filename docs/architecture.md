# 架构设计说明

## 设计目标

项目首先保证可解释、可测试和安全边界清晰，其次才是框架数量。默认本地模式用于开发与 CI，Docker 模式用于启用 PostgreSQL 与 Redis（pgvector 只做了列类型映射，未接 ANN 索引，理由见「向量后端」一节）。

相关文档：[系统架构图](diagrams/architecture.svg)｜[切块参数对照实验](chunking_experiment.md)｜[MCP 说明](mcp.md)｜[状态图](state_graph.md)

## 核心数据流

1. `/documents` 校验文件名、类型和大小，计算 SHA-256 去重。
2. 文档按页解析、规范化并重叠切块，交给当前向量后端生成向量：默认是 384 维本地 Hash Embedding，
   配好模型目录后换成 512 维本地 ONNX 语义模型（见下节「向量后端」）。切块粒度默认为 700/100，
   该取值有对照实验支撑（见 [chunking_experiment.md](chunking_experiment.md)）。
3. `/chat` 创建或验证会话后，先过两道**不调用模型**的前置判据：提示词注入拦截，以及语料范围判据
   （带设备序列号、算式或工单诉求的问法豁免后者）。两道都不命中才进入 Agent Loop：模型提出工具调用申请，
   服务端按白名单校验参数并执行，结果回填后继续，最多 5 轮。
4. 知识库检索是白名单里的普通工具（`search_knowledge_base`），由模型决定何时调用；设备查询、计算、工单同理。
5. RAG 计算三路分数后加权排序：单字重叠 0.30 + 二元字组 0.35 + 向量余弦 0.35；查询侧先剥掉虚词和语气词再做两字组合，因此「啥是合母」和「合母是什么」能落到同一段原文上。排序之后再用片段的行业标签做加减（见下节），把「机型场景不对」的依据压到后面。
6. 「模型」是一个接口：配置了远程服务就用远程模型，未配置时由本地规则模型复用 `graph.py` 的分类结果提出同样的工具申请。
7. 工单写操作在循环内就被拦下（`stopped_reason=needs_confirmation`），`SupportAgent` 换成待确认动作；`/tickets` 依次验签、验有效期、验归属，最后靠 `consumed_confirmation_tokens` 的主键冲突判定单次使用，通过后才写入。
8. 每一轮 `/chat` 都以一个服务端判定的终态收场（`status`）：`completed`、`degraded`、`pending_confirmation`、`needs_clarification`、`blocked`、`failed`。同时给出 `answer_source`（回答的依据是检索片段、结构化工具、模型自行作答，还是服务端规则话术）和 `retryable`（只有暂时性的模型故障才为真）。判定顺序即优先级，因此不会出现「给了确认令牌但回答是拒答」这类自相矛盾的返回。
9. 离线评测分三层（检索 / 工具选择 / 最终回答），并且复用线上代码：`run_turn` 是从 `respond` 里抽出来的无副作用版本，评测的检索层和回答层都调它，评的就是线上跑的那一次。

## 对话终态与服务端判定

`status` / `answer_source` / `retryable` 三个字段共同构成对外契约，客户端凭它渲染状态、
决定是否重试，离线评测也凭它把回答层按「凭什么答的」来判，而不是去猜回答文本。

| 分支 | `status` | `answer_source` | `retryable` |
|---|---|---|---|
| 提示词注入在进入循环前被拦下 | `blocked` | `policy` | `false` |
| 问题落在语料范围外（前置判定，模型零调用） | `needs_clarification` | `policy` | `false` |
| 循环拿到 `llm_error:*` | `degraded` | `fallback` | 沿用 `LLMError.retryable` |
| 循环拿到 `needs_confirmation` | `pending_confirmation` | `policy` | `false` |
| 检索过但一条依据都没有 | `failed` | `policy` | `false` |
| 有引用片段 | `completed` | `knowledge` | `false` |
| 有成功的设备查询或计算 | `completed` | `tool` | `false` |
| 模型没调工具直接作答 | `completed` | `model` | `false` |

只有 `needs_clarification` 会同时带上 `clarification`（`reason` + `hints`），
客户端据此把回答渲染成一次追问；这是它与 `pending_confirmation` 的分工——
后者在等一个同意/拒绝，前者在等一段新信息。

模型无法影响上表的判定，它只能提出工具申请和写一段文本；服务端保留覆盖权
（例如检索为空时把模型的话术换成拒答，或判定问题在语料范围外时换成追问）。
`degraded` 是否可重试不由服务端拍脑袋决定，
而是复用模型层对错误的分类：`rate_limit`、`service`、`network` 为真，
`authentication`、`request`、`invalid_response` 为假。

## 行业元数据与版本并列

普通 RAG 只按文字相似度排序，在光伏资料上会出错：同一份语料里「户用」「工商业」
「地面电站」讲同一件事用的词高度重合，纯文本分数分不出该用哪一份；不同版本的资料
对同一件事的说法也可能不同。所以切分阶段就给每个片段贴行业标签。

标签由词典和正则从**片段正文**确定性抽出（`services/industry.py`），不做任何猜测：

| 标签 | 来源 | 例子 |
|---|---|---|
| `manufacturer` | 语料编号推导 | `Huawei` |
| `device_models` | 机型词典 + 完整型号正则 | `SUN2000`、`SUN2000-100KTL-M1`、`LUNA2000` |
| `protocols` | 协议正则，长模式优先 | `Modbus TCP`、`RS485`、`IEC 104` |
| `document_version` | 文档标题或分册名 | `V2.0`、`第3册` |
| `scenario` | 语料编号映射 | `户用`、`地面电站`、`交直流屏柜` |
| `content_type` | 小节标题关键词 | `reference`、`procedure`、`faq` |

两个关键取舍：

- **标签必须从正文抽，不能只看标题。** 光伏资料的小节标题常是「6.2 绝缘阻抗故障位置定位」，
  真正提到 `RS485`、`SUN2000` 的是正文。只扫标题实测 95 个章节只命中 4 个机型、0 个协议，元数据等于没有。
- **抽不到就留空，不写默认值。** 元数据一旦不可信，拿它做排序比不做排序更危险。

检索时元数据**只影响排序，不做硬过滤**：查询里写了机型或场景，命中同类的片段加 0.06，
明确属于别类的降 0.10。理由是否则跨机型通用的章节会被一起杀掉，模型反而拿不到任何依据。
实测「户用逆变器怎么组网」在加权前第 2～5 条混着「地面电站逆变器产品」和跨模块速查，
加权后前几条收敛到户用的 2.2 / 2.6 组网章节；「储能柜的容量是多少」把无关分册的
「事故放电与容量校核」挤出前五。

**标签要短：它会被模型抄进回答。** 这行标签本是给模型核对依据用的，但模型会顺手把它写进回答，
所以 `describe_facets` 对机型列表做了归纳——超过 3 个（`industry.MODEL_LIST_LIMIT`）就写成
「N 个机型通用」，少数几个仍逐个列出（那正是「这段只适用这几款」的关键信息，不能省）。
起因是一次实测：语料里有片段一次列了 14 个型号，标签因此长达 224 字，而提示词当时两处都要求
「引用时说明这些标签」，于是一条绝缘阻抗排查的回答 1814 字里有 581 字（32%）是机型清单，
读起来像资料目录而不是排查指导。现在提示词改为「用一句短标签带过、不复述标签、不交代检索过程」，
同一问题降到 940 字且全是排查步骤。**版本与场景才是判断依据是否适用的关键，机型清单不是**——
一次列十几个型号，语义上等于「跨机型通用」，罗列反而没有区分度。

**版本并列提示。** 一次回答的依据如果落在两个及以上 `document_version` 上
（分数接近，差距在 15% 以内），`detect_conflicts` 会把它们并列返回在 `conflicts` 字段里，
前端渲染成提示条。语义是「依据来自两份不同资料，请按现场型号与厂家正式资料确认」，
**不是**断言两份资料互相矛盾——教材章节和分册资料讲同一件事，措辞详略本来就不同。
它要防的是模型「偷偷挑一个版本下结论」。系统提示词里也写死了这条要求。

这个机制依赖模型实际检索到的依据：模型把问题拆成多轮检索后，`conflicts` 可能为空
（依据集中在单一版本）。这是刻意的——提示必须和用户看到的引用对得上，
不能出现「提示了冲突却看不到冲突的那份引用」。

## 离线评测

评测拆成三层，因为一次错误回答可能错在任何一层：**检索没找到原文**、
**模型选错了工具**、**资料对了但回答不对**。混成一个总分看不出该修哪儿。

| 层 | 调用的线上代码 | 判据 |
|---|---|---|
| `retrieval` | `SupportAgent.retrieve` | Top-K 片段是否覆盖 `expected_keywords` |
| `tool` | `SupportAgent.run_turn` | `expected` 的工具都选到、`forbidden` 的一个没碰 |
| `answer` | `SupportAgent.run_turn` | `status` / `answer_source` 符合期望，回答含（或不含）指定文本 |

关键约束：**评测不自己实现判定**。`run_turn` 是从 `/chat` 里抽出来的无副作用版本
（跑完整链路、判出终态，但不建会话、不写消息、不签令牌），`/chat` 的 `respond` 在它之上
再加持久化。所以评测走的就是线上那一次检索、那一份分支判定，不存在「评测逻辑和线上逻辑各写一份、
慢慢漂移」的问题。

两个容易被忽略的判定细节：

- 工具层统计的是**选对工具**，不是「工具执行成功」。写操作被拦下待人工确认时 `ok=False`，
  但那正是设计要的行为，所以算选对；参数校验没过才算选错。
- 没声明期望的层不进分母。旧评测集只写顶层 `expected_keywords`，跑出来仍与升级前完全一致，
  且不触发任何模型调用。

## 工具容错

工具调用是整条链路里最不受控的一环：它可能查库、可能调外部接口，也可能因为参数不对被反复重试。
三件事在 `services/agent_loop.py` 里处理。

**每个工具带独立超时。** `ToolSpec.timeout_seconds` 默认 10 秒，需要查库的
`search_knowledge_base` 放宽到 15 秒。超时后返回 `error_kind="timeout"`，把「已放弃等待」
交回模型，而不是让整个请求挂在那里。

这里有一个必须绕开的坑：**同步 handler 不能直接在事件循环里调用。** 项目里 `calculator`
和 `query_device` 都是同步函数，如果直接 `await asyncio.wait_for(spec.handler(arguments), t)`，
这次调用会占住事件循环，`wait_for` 的计时器根本没有机会触发——**写成超时、实际不生效**，
是最容易蒙混过关的一种假安全。所以 `_invoke()` 先把同步 handler 丢进线程
（`asyncio.to_thread`）再等，超时才有意义。`test_sync_tool_is_run_in_a_thread_so_the_timeout_can_fire`
用一个 `time.sleep(0.3)` 的工具守着这条。

需要说清它的边界：**超时只是让调用方不再等待，并不能中止已经在跑的同步工具**，线程会继续跑到结束。
「超时」不等于「操作已回滚」。如果某个工具会写数据，它必须自己支持取消或者做成幂等，
否则会出现「用户看到超时、后台却已经改完」这种情况——这也是写操作一律不自动执行、
必须走确认令牌的另一个理由。

**同一个「工具 + 参数」连续失败两次后服务端不再放行。** `MAX_TOOL_RETRIES = 2`，第三次同样的请求
直接返回 `error_kind="repeated_failure"`，把「别再重试」当成确定信息交给模型。这不是补能力，
是控成本：模型把「工具失败」理解成「再试一次」时，一次提问会放大成几十次调用，每次都是真金白银。
判定用「工具名 + 参数原文」做键，所以换参数重试不受影响。写操作被拦下不计入失败——
它本来就要等人工确认，计数会把正常流程误判成原地打转。

**失败按类型分类。** `ToolOutcome.error_kind` 与 `ToolCallRecord.error_kind` 记下
`unknown_tool` / `invalid_arguments` / `needs_confirmation` / `timeout` / `tool_error` /
`internal_error` / `repeated_failure` 七种。有了它，审计与评测才能按类型统计
（「未知工具出现过几次」「超时集中在哪个工具」），而不是对着一堆中文错误串做关键词匹配。

## 写操作确认与四道闸

写操作在循环里就被拦下，`SupportAgent` 把它换成一次待确认动作和一张令牌。令牌落到 `/tickets`
时依次过四道闸，**顺序是有意的**：

1. **签名**（HMAC-SHA256）。改一个字符就验不过。判定自己担不起，因为 `secret` 在服务端，
   客户端拿不到，所以它无法自己造一张令牌。
2. **有效期**（`exp`，默认十分钟）。签名对不代表还能用——令牌可能是在别处签好、现在才递上来的。
3. **归属**（`action` 与 `user_id` 必须与请求一致）。这是防「拿别人的令牌办自己的事」。
4. **单次使用**。这一条与前三条不同：前三条是**无状态**判断，只看令牌本身；这条必须有地方记下
   「这张用过了」，所以它需要存储。

**验签必须排在判重之前。** 否则一张被改过的令牌会被判成「已经使用」，调用方从响应里就能
反推出「这张令牌存在过、并且被用掉了」——判重结果本身成了信息泄露。

**判据单独建表（`consumed_confirmation_tokens`），不寄居在 `audit_logs` 里。** 早先的实现是在审计表里
查一条 `confirmation_consumed` 记录，查到就返回 409。两个问题：

- 检查与写入之间有时间窗，并发下两个请求都查到「没人用过」，于是同一张令牌建出两条工单。
  现在 `token_hash` 就是主键，重复写入直接撞唯一约束，判定与占位压成一次原子操作——
  **把并发正确性交给数据库，而不是交给两次查询之间的时间差。**
- 审计记录是可以清理、可以轮转的，而防重放是判据。判据一旦跟着审计一起被删掉，
  安全属性就静默消失了。两者生命周期不同，不该共用一行。

消费记录与工单**在同一事务里提交**：提交失败时两者一起回滚，用户拿原令牌重试即可，
不会出现「令牌已经烧掉、工单却没建」。记录里只存 `token_hash`，不存令牌原文——令牌本身就是凭证，
落库等于多留一份可用的口令。

四道闸的行为可以一键复现：

```bash
python examples/confirmation_token_demo.py
```

它跑在临时库上，不连模型、不加载 ONNX 模型，四段结果固定是 201 / 409 / 400 / 400。

## 向量后端

向量生成从检索逻辑里拆了出来（`services/semantic.py`），因为不同场景要的东西不一样：
CI 要零依赖、本机演示要真语义，而这两件事不可能用同一个实现满足。

| 后端 | 维度 | 依赖 | 用途 |
|---|---|---|---|
| `hash` | 384 | 无 | 默认。CI 与无模型环境，只保证流程跑通 |
| `onnx` | 512 | `onnxruntime` + `tokenizers` + 模型目录 | 本地语义检索，离线、无 API 成本 |

几条明确的设计选择：

- 配置写了 `onnx` 但依赖或模型缺失时**直接报错**，不静默退回哈希向量。两者不是「差一点」，
  而是两个不同的向量空间，混用会让检索结果无法解释。
- **换后端必须重建表并重新导入语料**（`python scripts/ingest_smartpv.py --reset`），
  因为库里的旧向量和新查询向量不在一个空间。检索侧另有兜底：片段向量长度与当前查询
  不一致时，语义那一路记 0 并打警告——余弦相似度在长度不等时会按短的截断，静默给出一个
  看着正常的假分数，这比分数为 0 危险得多。
- 入库时把后端指纹（`hash:384` / `onnx:512`）写进片段元数据，库是哪套模型建的查得出来。
- 池化用 `[CLS]` 位（BGE 官方用法）。实测比平均池化分得更开：相关句子 +0.543、无关最高 +0.361
  （平均池化 +0.508 / +0.289）。
- 语义分要不要按词面覆盖率打折，由后端自己声明（`semantic_trust_floor`）：哈希向量必须打折
  （低覆盖率下的「相似」多半是常用字碰撞），真语义模型不打折。

实测语义向量带来的变化（212 片段语料，30 条带术语问题 + 10 条改写问法）：

- 库内 top1 分数：最低 0.226 → 0.324，中位 0.518 → 0.581
- 排序命中率（领域术语出现在 top-1）：83% → 87%（去掉词面打折后），top-3 都是 90%
- **分数阈值这条路更走不通了**：库外问题的 top1 最高从 0.353 涨到 0.486。真语义模型是懂
  人情世故的——「怎么考驾照」「车险怎么买」被它判定为和语料里「危险品运输管理」一节相关
  （原始语义 0.531，词面覆盖率甚至到 1.000，因为那节真的提到了驾驶证）。哈希向量之所以
  「分开」了库内库外，只是因为它随机。语料范围判据因此在语义向量下更不可替代。

## 有意保留的工程演进点

- **检索缓存与请求限流已接入**（`services/cache.py`）。两者共用一个 key-value 抽象：
  `MemoryStore`（进程内，本地开发与 CI 的默认路径）、`RedisStore`（配了 `REDIS_URL` 时启用）、
  `ResilientStore`（把前两者包起来的降级层）。缓存的是「命中哪些片段、各得多少分」而不是
  `SearchHit` 本身——后者是 ORM 对象，序列化进缓存既脆弱又容易和库里的数据脱节；命中缓存后
  按 id 回库取正文，片段被删掉时会自然少返回。
  失效走**语料代次**而不是删 key：导入文档时把代次 +1，新 key 天然带新代次，旧的靠 TTL 过期
  （Redis 下按前缀删要 SCAN 全库，代价远高于等它过期）。代价是绕过 `RAGService` 直接写库的
  路径（`scripts/ingest_document.py`）必须自己调一次 `invalidate()`，漏掉的表现很隐蔽——
  刚导进去的内容在 TTL 内查不到，看起来像导入失败。
  限流是固定窗口（窗口编号进 key，一次 `INCR` 判定），只挡在 `/chat` 入口：被拒的请求不建会话、
  不写消息、不调模型。
  **一条纪律：缓存服务不可用绝不能让接口不可用。** 实测本机配了 `REDIS_URL` 但 6379 没服务时，
  首次操作吃满 1 秒连接超时，之后靠熔断（默认冷却 30 秒）直接走进程内实现——没有熔断的话，
  每个请求都要吃一遍超时，接口会从「缓存失效」变成「整体变慢」。`/health` 的
  `cache.degraded` 会翻真，排障时先看它。
- **pgvector 记了但没接线，因为在本项目规模上找不到可验证的收益。** `document_chunks.embedding`
  在 PostgreSQL 下就是 `Vector(512)`，但既没有建 ANN 索引，也没有走 `<=>` 排序——检索仍在
  Python 里全量扫。想接 ANN 预筛会撞上一个硬约束：打分用的 IDF 权重依赖**全语料**的词频
  （`corpus_index()`），只取向量近邻候选就没法算出这份 df，除非把词频统计挪到入库时落库。
  212 片段的全量扫代价可以忽略，所以这一步的收益为零，做成「有开关但从不触发」的代码
  只会增加解释成本。真正要做时的顺序是：先把 df 落库，再加 ANN 预筛与索引。
- 当前小数据集在应用层计算混合得分（单字重叠 0.30 + 二元字组 0.35 + 向量 0.35，查询侧先剥虚词，
  再加元数据加减分）；数据量上升后按上一条的顺序改造。
- **拒答不靠分数阈值，靠语料范围判据。** `RETRIEVAL_MIN_SCORE` 仍是 0.0，
  承担判定的是 `RAGService.corpus_scope_reason()`：查询的两字组合在整份语料里的缺失比例达到 0.60，
  或者查询里的外文词语料一个都不认识（`Python`、`Windows`），就判为语料外。
  实测 30 条库内问题全部放行、30 条库外问题全部拦下，无误拦无漏放；样本留在
  `D:\资料汇总\拓展资料\检索范围样本.jsonl`。
  为什么不设分数阈值：哈希向量只是字符碰撞，试过 IDF 的四种加权变体、剔除语料外词、
  跨词词组凝固度过滤，库内与库外的分数分布**始终重叠**；换成真语义向量后重叠**更严重**
  （库外最高 0.353 → 0.486）。语义相似度也试过当判据——取「问题与语料最像那段」的余弦，
  库外最高 0.604、库内最低 0.505，同样重叠。**结论是「问题是否属于这份资料」这个判断，
  在词汇与语义两个维度上都做不到干净分离，只能选一个工作点并承认代价。**
  这条判据的判定必须前置在调用模型之前：实测模型遇到跑题问题根本不去调检索工具，
  而是直接凭「我是光伏助手」拒答，那样服务端的兜底永远等不到。
- **命中判据时不拒答，改成追问。** 判据是词汇层面的近似，10 条改写问法
  （「天太热机器会不会自己降低出力」「柜子里一直嗡嗡响，是不是坏了」）里有 7 条因为
  「问题用的词语料里没出现过」被它拦下，而它们问的确实是这份资料里的事（温度降额、异响排查）。
  提高缺失比例上限会让库外问题一并放进来，词面与语义两个维度都试不出干净的分界线，
  于是保留这个工作点、只改变代价的形态：命中后返回 `status=needs_clarification`、
  `answer_source=policy`，并带上 `clarification`（`reason` 说明是哪条判据命中、
  `hints` 列出建议补充的信息），请用户补一句设备型号或现象再问一次。
  **误拦本身没有消失，它只是从「答不出」变成「多问一句」。**
  两种原因给不同话术：措辞对不上时提示换成本领域说法，外文词全不认识时先说明这份资料不覆盖、
  再把人引回现场设备问题。追问仍由服务端给出，模型一次都不调用。
- **带结构化锚点的问题要先豁免判据。** 判据问的是「这个问题属于这份资料吗」，
  而设备查询、算术、建工单这几类问题由工具承接、压根不查这份资料，拿同一把尺子量会量错。
  实测踩到的两种误判：`SN-2024-000123 这台设备现在什么状态` 的词组缺失比例 0.62、
  `帮我建个工单` 0.67，两条都被判成跑题返回追问，`query_device` 与 `create_ticket`
  于是永远走不到；而同一件事换个说法（`设备 SN-2024-000123 现在是什么状态`，缺失 0.50）
  就能通过——拦下它们的不是「话题不相关」，而是「措辞没对上语料」。
  `services/tools.py::has_structured_anchor()` 认三类锚点：设备序列号、算术表达式
  （`100*0.986`、`100 乘以 0.986`）、工单诉求（`工单` / `报修` / `派单` / `转人工` / `投诉`），
  命中就跳过判据、交给模型去选工具。锚点只证明「有工具可答」，不证明「答得出来」——
  查不到的序列号仍由工具自己报错。**判据本身一个字没改**，跑题问题照旧被拦下。
  这一类缺口只有把语料撑到判据的启用门槛（60 片段）才会显形，
  所以集成测试用 `_seed_identical_chunks()` 造够片段数，并留了一条跑题对照组守着。
- **结构化点表尚未建立。** 行业设计里的 `lookup_register`（按厂家 + 型号 + 协议版本 +
  寄存地址精确查询）、`convert_register_value`、`compare_protocol_versions` 需要一个独立的
  点表数据源，当前语料里没有寄存器地址表（实测 0 条），因此没有实现，也没有用假数据顶上。
  这一步要等选定脱敏点表资料之后再做。
- `create_all` 适合演示；正式环境应改用 Alembic 迁移。
- 模型已经能自主选择工具并可稳定测试；`graph.py` 的规则分类降级为本地规则模型的判据，服务端白名单、参数校验与权限判断始终保留。
- Agent Loop 的工具结果尚未做长度截断与内容隔离；工具返回的文本可能携带来自文档的注入内容，需要按不可信输入处理。

## 安全边界

- 文件名使用 `Path.name`，不信任客户端路径。
- 上传大小受限，文件类型使用白名单。
- 会话按用户隔离，跨用户访问返回 404/403。
- 计算器使用 AST 白名单，不使用 `eval`。
- 模型不能直接执行写工具；工单必须二次确认。
- 确认令牌带签名、十分钟有效期、绑定用户并且单次使用；单次使用由 `consumed_confirmation_tokens` 的主键约束保证，并发下也不会重复放行。
- 模型服务错误不会丢失已经写入的用户消息。
