# 架构设计说明

## 设计目标

项目首先保证可解释、可测试和安全边界清晰，其次才是框架数量。默认本地模式用于学习和 CI，Docker 模式用于展示 PostgreSQL/pgvector 与 Redis 技术栈。

## 核心数据流

1. `/documents` 校验文件名、类型和大小，计算 SHA-256 去重。
2. 文档按页解析、规范化并重叠切块，生成 384 维本地 Hash Embedding。
3. `/chat` 创建或验证会话，先做确定性的提示词注入拦截，再进入 Agent Loop：模型提出工具调用申请，服务端按白名单校验参数并执行，结果回填后继续，最多 5 轮。
4. 知识库检索是白名单里的普通工具（`search_knowledge_base`），由模型决定何时调用；订单、计算、工单同理。
5. RAG 同时计算词项重合和向量余弦分数，按 0.55/0.45 加权排序。
6. 「模型」是一个接口：配置了远程服务就用远程模型，未配置时由本地规则模型复用 `graph.py` 的分类结果提出同样的工具申请。
7. 工单写操作在循环内就被拦下（`stopped_reason=needs_confirmation`），`SupportAgent` 换成待确认动作；`/tickets` 验证 HMAC 令牌、用户、有效期和防重放记录后才写入。

## 数据表

| 表 | 作用 | 关键约束 |
|---|---|---|
| `conversations` | 会话所有权 | `user_id` 建索引 |
| `messages` | 用户和助手消息 | 外键关联会话 |
| `source_documents` | 原始文档元数据 | `checksum` 唯一 |
| `document_chunks` | 文本、页码和向量 | 文档外键、384 维 Vector |
| `tickets` | 模拟工单 | 会话外键 |
| `feedback` | 回答反馈 | 消息外键 |
| `evaluation_runs` | 评测结果 | 保存逐条详情 |
| `audit_logs` | 安全和写操作审计 | action/resource 索引 |

## 有意保留的工程演进点

- 本地 Hash Embedding 仅用于零成本演示；下一步接入真实中英文 Embedding，并做向量批量写入。
- 当前小数据集在应用层计算混合得分；数据量上升后，使用 pgvector ANN 索引、PostgreSQL 全文检索和 RRF 融合。
- Redis 已提供 Compose 服务，但缓存与分布式限流留作第 6 周练习，避免隐藏关键逻辑。
- `create_all` 适合演示；正式环境应改用 Alembic 迁移。
- 模型已经能自主选择工具并可稳定测试；`graph.py` 的规则分类降级为本地规则模型的判据，服务端白名单、参数校验与权限判断始终保留。
- Agent Loop 的工具结果尚未做长度截断与内容隔离；工具返回的文本可能携带来自文档的注入内容，需要按不可信输入处理。

## 安全边界

- 文件名使用 `Path.name`，不信任客户端路径。
- 上传大小受限，文件类型使用白名单。
- 会话按用户隔离，跨用户访问返回 404/403。
- 计算器使用 AST 白名单，不使用 `eval`。
- 模型不能直接执行写工具；工单必须二次确认。
- 确认令牌带签名、十分钟有效期、绑定用户并且单次使用。
- 模型服务错误不会丢失已经写入的用户消息。
